# HKEI OS v2 — OpenAI Semantic Adjudication Provider Specification

## 1. Purpose

A future concrete OpenAI adapter maps `SemanticAdjudicationRequest` into an
OpenAI API request and maps provider output into
`SemanticAdjudicationResponse`. It remains an adapter and must not own Gate
logic, candidate construction, final resolution, Reader Intent, Risk, or
benchmark knowledge.

## 2. Architectural Position

```text
Deterministic Editorial Analysis
→ Adjudication Gate
→ Request Builder
→ OpenAISemanticAdjudicationProvider
→ Response Validator
→ future Resolver
```

The provider must not bypass an earlier or later layer.

## 3. API Design Principle

Prefer the current OpenAI Responses API and a supported structured-output
mechanism available in the installed official SDK at implementation time. The
implementation task must verify the exact supported SDK interface against
official OpenAI documentation before coding. Do not freeze obsolete Chat
Completions syntax into the architecture.

## 4. Structured Output Requirement

Request schema-constrained output for the adjudication payload. A prompt that
merely asks the model to “return JSON” is insufficient. Use OpenAI Structured
Outputs when supported by the selected model and SDK.

## 5. Provider Input

The provider receives only `SemanticAdjudicationRequest` and
`SemanticAdjudicationRuntimeContext`. It must not receive benchmark expected
labels, risk annotations, Reader Intent, a generation prompt, the full source
object, or raw credentials outside the runtime context.

## 6. Minimal Source Text

Send only `title`, `lead`, and `body_excerpt` as prepared by the Request
Builder. Do not fetch or reconstruct full article text.

## 7. Candidate Restrictions

`adjudicated_topic` must be selected only from `request.candidate_topics`, and
`adjudicated_format` only from `request.candidate_formats`. Represent these
legal sets explicitly in both instructions and the structured schema where
practical.

## 8. Scope Awareness

The frozen Request Builder supplies the candidate sets. When a dimension has
one candidate, preserve it. The provider must not reconsider a dimension the
Gate did not open.

## 9. System Instruction

The future instruction should concisely establish that the model is an
editorial semantic adjudicator; may classify only dimensions represented by
the supplied legal candidates; must choose exactly one Topic and one Editorial
Format; must rely only on supplied source text and structured evidence; must
not invent facts, perform factual verification, or use unnecessary external
knowledge; and may return only concise rationale and evidence references, not
chain-of-thought. This specification does not freeze exact prompt wording.

## 10. No Chain-of-Thought

Never request hidden reasoning, detailed chain-of-thought, or step-by-step
internal reasoning. Request only selected labels, categorical confidence,
concise rationale, evidence references, an ambiguity flag, and warnings.

## 11. Semantic Task Boundary

The model determines the primary editorial Topic and/or Editorial Format. It
does not determine truth, Risk, attribution requirements, generation output,
or final Reader Intent.

## 12. Structured Output Schema

Conceptually, model-generated output is:

```json
{
  "adjudicated_topic": "<candidate>",
  "adjudicated_format": "<candidate>",
  "topic_confidence": "HIGH|MEDIUM|LOW",
  "format_confidence": "HIGH|MEDIUM|LOW",
  "topic_reason": "...",
  "format_reason": "...",
  "topic_evidence_refs": ["HEADLINE", "LEAD"],
  "format_evidence_refs": ["HEADLINE", "LEAD"],
  "ambiguity_remaining": false,
  "warnings": []
}
```

Provider metadata and usage are added by the adapter, not generated by the
model.

## 13. Provider Metadata

The model must not generate `provider`, `model`, `request_schema_version`,
`response_schema_version`, `input_fingerprint`, `usage_input_tokens`, or
`usage_output_tokens`. The adapter populates them from trusted runtime and API
metadata.

## 14. Evidence References

Allowed references correspond only to supplied material:

- `HEADLINE`
- `LEAD`
- `BODY_EXCERPT`
- `CONTEXTUAL_SUPPORTS`
- `SEMANTIC_RELATIONSHIPS`
- `PRIMARY_DOMAIN_CANDIDATES`
- `SECONDARY_DOMAIN_CANDIDATES`
- `FORMAT_SUPPORT`
- `FORMAT_SUPPRESSION`

Do not request unavailable sentence indexes.

## 15. Request Payload Structure

The conceptual payload contains:

1. Task.
2. Source: title, lead, and body excerpt.
3. Current deterministic result: Topic and confidence, Format and confidence,
   and content type.
4. Structured evidence: contextual supports and suppressions, semantic
   relationship summary, primary and secondary candidates, format support and
   suppression, reason codes, and warnings.
5. Legal candidates: Topic and Format candidate sets.

## 16. Prompt Injection Boundary

Treat source text as untrusted quoted content. Clearly delimit `title`, `lead`,
and `body_excerpt` from provider instructions. Instructions found inside source
text must never override the adjudication instructions.

## 17. External Knowledge

Use supplied evidence as the basis of classification. MVP adjudication enables
no web browsing, tools, code execution, file access, or external retrieval.

## 18. Tool Calling

MVP requires no tool calls. Use direct structured model output.

## 19. Temperature

Use `runtime_context.temperature`; do not hard-code temperature in the adapter.

## 20. Maximum Output Tokens

Use `runtime_context.max_output_tokens`. Do not silently override it except
where SDK/API validation requires handling an invalid configuration.

## 21. Timeout

Use `runtime_context.timeout_seconds`. Map provider timeouts into
`SemanticAdjudicationProviderTimeoutError`.

## 22. Retries

Use `runtime_context.max_retries` only for bounded retries of transient provider
or API failures. Do not retry structurally invalid classifications, candidate
violations, fingerprint mismatch, or semantic ambiguity.

## 23. Provider Unavailable Mapping

Map temporary provider or network availability failures into
`SemanticAdjudicationProviderUnavailableError`. Never expose raw credentials.

## 24. Configuration Mapping

Map missing or invalid OpenAI runtime configuration—including a missing API
key, invalid configured model before request, or disabled provider—into
`SemanticAdjudicationProviderConfigurationError`, without leaking secrets.

## 25. Invalid Output Mapping

Malformed structured output, missing required output, unknown confidence,
refusal without valid adjudication, and parsing failure map into
`SemanticAdjudicationProviderInvalidResponseError`. The existing response
validator remains final contract authority.

## 26. Refusal Handling

A Structured Outputs refusal must never be converted into invented labels.
Treat it as provider output that cannot produce valid adjudication, mapping it
to provider-level invalid or unavailable behavior according to implementation
semantics. Any diagnostic text must be concise and omit source bodies and
secrets.

## 27. Truncation and Incomplete Output

If an output token limit, stop condition, or incomplete response prevents valid
structured completion, do not guess missing fields. Raise
`SemanticAdjudicationProviderInvalidResponseError` unless the SDK exposes a
more appropriate temporary/provider error category.

## 28. Candidate Membership Double Protection

Candidate membership is protected by both structured provider schema and
instructions, and by `SemanticAdjudicationResponseValidator`. The adapter must
not remove the second layer.

## 29. Confidence Mapping

Map only `HIGH`, `MEDIUM`, or `LOW` to `AdjudicationConfidence`. Do not trust
arbitrary numeric probabilities or expose log probabilities as adjudication
confidence.

## 30. Ambiguity

`ambiguity_remaining=True` is valid. The future Resolver decides how to use a
structurally valid but ambiguous response; the provider owns no ambiguity
policy.

## 31. Warnings

Allow concise warnings such as “source evidence is mixed” or “topic remains
ambiguous.” Warnings must not become free-form essays.

## 32. Usage Metadata

Capture trusted API input/output token usage when available. If it is
unavailable after a successful request, use a deterministic fallback such as
zero only when the implementation contract explicitly permits it. Never
estimate token counts manually.

## 33. Input Fingerprint

Copy `request.input_fingerprint` exactly into the response. The model must not
generate it.

## 34. Provider Identity

Set response provider to `"openai"`. Set response model to the actual
configured or returned identifier, preferring trusted API response metadata
when available.

## 35. Schema Versions

Initial conceptual adapter constants are:

```text
OPENAI_ADJUDICATION_REQUEST_SCHEMA_VERSION = "1.0"
OPENAI_ADJUDICATION_RESPONSE_SCHEMA_VERSION = "1.0"
```

These are HKEI adapter schema versions, not OpenAI API versions.

## 36. API Version Independence

Do not encode OpenAI API version strings in core adjudication domain models.
Transport and version details belong inside the concrete adapter.

## 37. SDK Boundary

Only the future concrete OpenAI adapter package/module may import the official
OpenAI Python SDK. Core adjudication modules remain free of OpenAI imports.

## 38. Client Injection

Allow OpenAI client injection into the concrete provider for tests. This must
support fake SDK responses and timeout, refusal, and malformed-response
simulation without network calls. Do not require global client state.

## 39. No Environment Lookup in Provider

The provider receives a `SemanticAdjudicationRuntimeContext` containing the
resolved API key. It must not call `os.getenv` or `os.environ`; secret resolution
stays outside the provider.

## 40. No Global Client

Avoid a process-global singleton OpenAI client. The provider instance owns or
receives its client.

## 41. Transport Error Sanitization

Map raw transport errors into concise provider-neutral messages. Do not expose
payloads that might contain credentials, source text, or request material.

## 42. Logging

Do not log API keys, full prompts, full articles, or raw provider responses.
Future structured diagnostics may include provider, model, request fingerprint,
latency, usage, and error category; logging is outside MVP implementation.

## 43. Deterministic Prompt Construction

Identical request, runtime context, and schema version must produce the same
logical prompt and schema. Do not add timestamps or random identifiers.

## 44. Request ID

The request ID may be included as non-secret correlation metadata when
supported, but it must not influence classification.

## 45. Output Validation Sequence

The future provider flow is:

1. Verify runtime configuration.
2. Construct deterministic prompt and schema.
3. Call OpenAI.
4. Detect transport/provider failure.
5. Detect refusal or incomplete output.
6. Parse the structured result.
7. Map confidence enum.
8. Construct `SemanticAdjudicationResponse`.
9. Return the response.
10. Let the external workflow call `SemanticAdjudicationResponseValidator`.

The adapter and validator must remain separate.

## 46. Failure Principle

Provider failure must never alter deterministic editorial output. The shadow
workflow provides deterministic fallback; a future Resolver must preserve this
fail-open property.

## 47. Model Selection

Use `runtime_context.model`; do not hard-code a model. Deployment/configuration
must verify eligibility against current OpenAI capabilities.

## 48. Structured-Output Capability

Deployment must select an OpenAI model/API path supporting the required
structured-output contract. If the configured model does not support it, raise
`SemanticAdjudicationProviderConfigurationError`; never silently fall back to
unconstrained plain text.

## 49. Cost Boundary

Only cases admitted by the frozen Gate reach the provider. The adapter must not
widen adjudication scope independently.

## 50. Non-Goals

This specification includes no implementation, network request, SDK
installation, model benchmark, prompt tuning, Resolver, cache, streaming, tool
use, web retrieval, or Risk, Claim, or Reader Intent adjudication.

## 51. Testing Requirements for Future Implementation

Future tests must simulate valid structured output; Topic-only, Format-only,
and combined adjudication; refusal; malformed output; unsupported candidates;
timeout; temporary API failure; configuration failure; incomplete/truncated
output; usage and model metadata; fingerprint preservation; no environment
lookup; and no network in unit tests.

## 52. Acceptance Criteria

The future implementation must preserve the OpenAI adapter boundary,
schema-constrained output, candidate restriction, prompt-injection boundary,
refusal and incomplete-output handling, provider-neutral error mapping,
categorical confidence mapping, trusted usage metadata, secret isolation,
client injection, no chain-of-thought, no external tools, and independence of
core HKEI architecture from OpenAI.
